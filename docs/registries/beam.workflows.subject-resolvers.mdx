# Workflow subject resolvers

`beam.workflows.subject-resolvers` maps a **kind** slug to a finder that loads the managed record.
The generic workflow endpoints address a record as a kind plus an id (`workflow-subjects/{kind}/{id}`)
and use this registry to turn that pair back into a model. Register one line per managed type and the
generic actuation surface works for it, with no endpoint of your own.

## Registering a resolver

The entry is a callable that takes the id and returns the model, or `null` when there is none:

```php
use Splicewire\Beam\Workflows\Control\SubjectResolverRegistry;

app(SubjectResolverRegistry::class)->register(
    'composition',
    fn (string $id) => Str::isUuid($id) ? Composition::find($id) : null,
);
```

Check the id's shape before querying, as above. The id comes straight from a URL, and a value your
database cannot compare should answer `null`, not raise.

## Unknown means not found

An unregistered kind, a kind that isn't a legal key and a record that doesn't exist all answer
`null`, and the endpoint turns that into a 404. A garbage slug in a URL stays a 404 rather than
becoming a server error.

## Two readings of resolve()

`resolve($kind, $id)` runs the finder and returns the model. `resolve($kind)` without an id returns
the finder itself, the way every other registry returns its entry. Callers that want the model always
pass the id.
