# Workflow effects

`beam.workflows.effects` holds every **effect**: code that runs after a transition has been applied,
such as notifying someone, calling a webhook or releasing a resource. It mirrors
[guards](beam.workflows.guards). A transition names its effects and fills their params, and the code
itself lives here, so a definition never carries executable logic.

## Registering an effect

An effect receives the `WorkflowTransitioned` event and the params the definition set for it:

```php
use Splicewire\Beam\Workflows\Control\TransitionEffectRegistry;

app(TransitionEffectRegistry::class)->register(
    'training-run.release',
    app(ReleaseWorkloadEffect::class),
    label: "Release the run's cloud workload",
);
```

**Pass `label:` and `paramsSchema:` by name.** A positional label lands in the `$by` slot, which is
also a string, so nothing fails and the label is quietly lost.

The package registers one effect itself: `workflow.await`, which notifies the named recipients and
adds a "waiting on you" item to their inbox. It stays dormant until the host binds a store for those
items.

## Effects never undo a transition

Effects run after the transition is committed, one at a time, and each is isolated: an effect that
throws is reported and the next one still runs. A failing notification can never roll back the
state change that triggered it. Anything that must decide whether the transition happens belongs in
a guard instead.

## Who reads it

- The lifecycle service, after each transition, for the effects that transition names.
- The blueprint validator, which rejects a definition that names an unregistered effect.
- The Workflows admin and editor, which offer the effect catalog (name, label and params schema) as a
  menu.
